GET /live — current sensor data

Everything the device is reporting right now, in one request: the newest frame published on the MQTT data topic, plus whether the device is online.

This is the same data the live dashboard shows. Nothing is stored and nothing is written to D1.

MethodGET
Path/live
Authnone (public read)
CORSaccess-control-allow-origin: *
Cacheno-store — always the moment of the request
Typical time0.7–1.5 s; up to ~6 s when the first session is retried

Try it: API Tester → Live sensors — the card sends the request and summarises online state, GPS fix, speed, satellites, roll/pitch, MPU temperature and chip temperature.

Request


GET /live?key=race-tracker HTTP/1.1
Host: race-tracker-history.pages.dev

No headers are required and no body is sent.

QueryTypeDefaultNotes
keystringrace-trackerMQTT topic key, 1–32 chars of A-Z a-z 0-9 _ -

The key selects the topics esp32-dash/<key>/data and esp32-dash/<key>/status; it is not a secret. The device's ingest key (X-Ingest-Key) has nothing to do with this endpoint and is never used here.

curl:


curl -sS -i "https://race-tracker-history.pages.dev/live?key=race-tracker"

Top-level fields

FieldTypeMeaning
okbooleanAlways true on 200
topicstringThe data topic that was read
onlineboolean \nulltrue = the device's retained status is online; false = last will says offline; null = no status retained yet (unknown)
retainedbooleantrue when the frame came from the broker's retained slot, i.e. the latest published frame even if the device is now offline
retrieved_msnumberEpoch milliseconds when the relay collected the frame
frameobjectThe MQTT payload, exactly as published; see mqtt.md for every field

frame and its blocks are the device's own JSON, so a field the firmware does not send is simply absent. If the payload were ever not JSON, frame would be the raw string instead of an object.

The two temperatures are different sensors:

  • frame.temp — MPU6050 die temperature, normal range roughly 25–45 °C
  • frame.sys.temp_c — ESP32 chip temperature, often 50–85 °C; the junction

    • limit is 125 °C

frame.ts is the device clock in epoch seconds, so a frame can be a second or two old even when online is true.

Errors

All errors use the API's JSON shape {"ok":false,"error":"<code>"}.

StatuserrorCauseWhat to do
400bad-keykey fails the 1–32 char [A-Za-z0-9_-] ruleFix the query string
502broker-unreachableThe relay could not open a TCP connection to the public brokerRetry in a moment
502broker-refusedThe broker answered CONNACK with a non-zero codeRetry; if it persists the broker is refusing new sessions
504live-timeoutNo data frame after two capped attempts (~6 s)The key may be wrong, or the device has never published a retained frame on that topic

A topic that has never been used returns 504 live-timeout, not 404: the broker has nothing retained to send, so there is no frame to return.

Example:


{ "ok": false, "error": "bad-key" }

How it works


GET /live ──▶ Pages Function ──▶ MQTT CONNECT ──▶ broker.hivemq.com:1883
                                      │
                                      ├─ SUBSCRIBE esp32-dash/<key>/data
                                      └─ SUBSCRIBE esp32-dash/<key>/status
                                      ▼
                          retained DATA + STATUS ──▶ JSON response
                                      ▼
                                  DISCONNECT
  • One outbound TCP session per attempt (at most two), opened with the runtime's

    • cloudflare:sockets API and closed as soon as the retained frame arrives.

  • No D1 read, no D1 write, no new topic, no firmware change: the broker already

    • keeps the last message, so there is nothing to copy.

  • The status subscribe is best-effort: a frame still returns with

    • "online": null if the status message does not arrive within 300 ms.

  • Each attempt is capped at 3 s, and the public broker's habit of accepting a

    • TCP connection and then going quiet is covered by one retry with a fresh session (~6 s worst case). Because every call opens a broker session, poll at most about once per second — the device only publishes once per second, so faster polling just repeats the same frame.

The implementation is split into a pure packet codec (worker/src/mqtt-wire.js), a socket-free state machine (worker/src/live.js) and the TCP transport (worker/src/live-tcp.js), which is imported lazily so the Node tests never need cloudflare:sockets.
